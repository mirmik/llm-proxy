# Восстановленный голосовой ввод AtomHome

16 сентября 2026, Nemor #2394. Пользователь выбрал локальную openWakeWord
«Хида́ри». По следующему запросу пользователя добавлено необязательное
озвучивание через VoxCPM2, Nemor #2413: только в ответ на голосовой ввод.

## Действующий тракт

```text
reSpeaker XVF3800, два канала, 16 кГц
  → локальная openWakeWord «Хидари»
  → буфер начала фразы + Silero VAD для определения конца
  → GigaAM-v3 на Aurora (.61), Whisper large-v3 на AionShad (.90) как резерв
  → Nemor на самом AtomHome (.76), персонаж atom, сессия main
  → текстовый ответ + VoxCPM2 по профилю atom-tts (.173 → .90)
  → ALSA default на .76, mono float32 48 кГц
```

Служба: `nemor-voice-assistant.service`, user systemd, включён автозапуск.
Старое имя `nemor-voice-input.service` на этом устройстве не существует.
Web UI: http://192.168.0.76:9090/

## Что было неисправно и что изменилось

Старый Nemor продолжал работать, но голосовая служба была disabled/inactive.
STT адреса `.90/.61:5055` перестали обслуживаться, старый токен отозван.
Клиент был настроен на Atom v3, использовал только канал 0 и другой порог.
В STT-подсказке оставался старый текст про «глюк системы» и «системное эхо».

Теперь STT использует действующий `inference-link` client с аутентификацией,
TLS pinning и Unicode prompt header v1. Подсказка только «Хидари.».
На трёх сохранённых командах GigaAM лучше сохранил командную часть, хотя
ошибки имени остались у обеих моделей. Это небольшой сравнительный smoke,
не полноценная оценка STT.

Обработка OWW строго каждые 1280 свежих сэмплов (80 мс), отдельно от VAD
с шагом 512 сэмплов: один и тот же cached score не считается несколькими
подтверждениями. Wakeword открывает фразу с предшествующим буфером, VAD
определяет конец; речь без обращения не попадает в STT.

Чтение ALSA идёт в отдельном потоке, в том числе во время сетевых запросов.
Очередь ограничена 16 VAD-кадрами. После ответа устаревший звук удаляется.
При потере кадров контекст сбрасывается. На первой живой пробе обнаружен
цикл сбросов: reset openWakeWord сам занимает заметное время и успевает
заполнить очередь. Исправление: очищать очередь **после** reset и начинать
со свежего кадра, не повторяя reset из-за аудио, поступившего во время него.

WS подписан на нужные сессию/персонажа; события других сессий и turn_id
не принимаются как ответ текущему запросу. Возврат к прослушиванию не ждёт
неограниченной тишины в комнате, как в старом коде.

## Границы текущей версии

Во время STT и ответа агента новые обращения пока не принимаются. При долгом
ответе это заметная пауза; задержка и политика повторных обращений вынесены
в #2410. Непрерывный приём/перебивание — отдельная работа.
Ложное «Хикари» и качество распознавания речи остаются ограничениями моделей.
Несколько комнат, серверное подтверждение кандидатов и отделение
голоса владельца пока не внедрены. В этой работе восстановлен один домашний
вход, а не завершена вся система голосового агента.

## TTS в llm-proxy

На AionShad (.90) добавлен ручной runtime `voxcpm2`: потоковый PCM float32
mono 48 кГц, `autoload=false`, `on_demand=false`. Проверены запуск, синтез,
остановка и повторный запуск. Для проверки озвучивания модель запущена вручную.
См. `~/project/llm-proxy/TTS.md` и `TTS_VERIFICATION.md`.

AtomHome использует `/v1/audio/speech` выбранного по профилю сервера с отдельным
TTS-токеном. Частота и формат проверяются по заголовкам
ответа. PCM поступает в `aplay -D default` потоком; неполные float32-сэмплы
между сетевыми чтениями сохраняются. Очередь ограничена 64 частями текста,
каждая не длиннее 500 символов; старые ответы после отмены не воспроизводятся.

**Голосовой вывод только на голосовой ввод.** Каждый отправленный клиентом
голосовой запрос получает уникальный `external_turn_id`. Клиент связывает
его с подтверждённым Nemor `turn_id` и принимает только события этого хода.
Текстовые сообщения, включая одновременные в той же сессии, не озвучиваются.

Перед первым предложением ответа проверяется доступность выбранной модели.
При выключенной/занятой модели, недоступной машине или ошибке потока
оставшаяся озвучка этого ответа пропускается. Следующий голосовой ответ
проверяет модель заново. Загрузка модели и повтор старых ответов не выполняются.
Тайм-аут health/connect — 0,4 с, чтения потока — 2 с без новых данных.
Вывод звука также имеет ограничение ожидания; текстовый ответ сохраняется.
Во время ответа и воспроизведения новые обращения пока не принимаются (#2410).

Ручное управление на .90:

```bash
llm-proxy start voxcpm2 --port 8081
llm-proxy stop voxcpm2 --port 8081
```

  длинный текст, очистка эмодзи и прежние проверки STT/аудиоввода.

## VoxCPM2 на RTX 3090 Ti и профиль atom-tts

Позднее 16 сентября, #2416: основной TTS перенесён на .173 (RTX 3090 Ti,
24 ГиБ), чтобы освободить RTX 5090 на .90 для Qwen3.8 NVFP4.
На .173 `qwen3.8-27b-uncensored-q4-mtp` остановлена, `autoload=false`,
`on_demand=false`. Поэтому LLM-резерв Atom через .61 → .173 пока выключен;
основная Qwen на .90 продолжает работать.

Профиль `atom-tts` в `~/.config/llm.json` на .76:

1. `https://192.168.0.173:8080`, voice `voxcpm2`, отдельный токен,
   проверка SHA256 сертификата через inference-link.
2. `http://192.168.0.90:8080`, voice `voxcpm2`, прежний TTS-токен.

Оба runtime VoxCPM2 имеют `autoload=false`, `on_demand=false`.
На .173 модель оставлена запущенной вручную; на .90 выключена.
Для отключения озвучки достаточно остановить доступные TTS runtime или
поставить `tts_enabled=false` в голосовой конфигурации и перезапустить службу.

Клиент `ProfileTTS` загружает профиль через inference-link, использует его
auth/TLS, но проверяет именно `/tts/health?voice=voxcpm2`: статус 200 и
`busy=false`. Стандартный старый TTSClient inference-link здесь не используется,
поскольку он ещё не поддерживает этот потоковый PCM-контракт.
Приоритет пересматривается для каждого голосового ответа. Резерв возможен
до первого выданного PCM; после начала аудио сбой отключает оставшийся ответ
без повторения уже услышанного. При выключенных обеих моделях проверка на .76
завершилась за 26 мс, следующая реплика после запуска снова озвучивается.

На .173:

- runtime: `voxcpm2`, порт backend 5052 (loopback);
- Python: `~/project/llm-proxy/.venv-voxcpm2/bin/python`, CPython 3.12.13;
- PyTorch 2.10.0+cu128, VoxCPM 2.0.3; зависимости перенесены из проверенного
  окружения Grim на .90, совместимость CUDA проверена на устройстве;
- веса: `~/project/models/VoxCPM2`, revision
  `32279effe8c19989596f05d353d1447f51d9e915`;
- reference: `~/.config/llm-proxy/voices/voxcpm2-reference.wav`;
- cfg=2, seed=42, 7 шагов, 4 CPU-потока; PCM float32 mono 48 кГц;
- после ранней инициализации CUDA в runner два последовательных старта
  прошли успешно (30,6 и 26,6 с). Первый старт до этой правки не увидел CUDA;
  точная причина исходного сбоя не установлена;
- память GPU после синтеза около 6474 MiB.

Замеры с .76 через HTTPS, три фразы:

| Шаги | Первый PCM | Время синтеза / длительность аудио |

| 10 | 0,19–0,23 с | 1,10–1,16 (медленнее воспроизведения) |
| 7 | 0,15–0,19 с | 0,87–0,92 (быстрее воспроизведения) |

На 7 шагах фраза длительностью 5,28 с синтезирована за 4,61 с.
Слышимое качество после изменения числа шагов требует подтверждения пользователя.
